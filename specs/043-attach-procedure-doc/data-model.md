# Phase 1 Data Model: Procedure Document On A Ritual Definition

One nullable column and one foreign key. No new table, no new index, no new enum, no
migration of existing rows.

---

## Changed entity: `collaboration.ritual_definition`

| Column | Type | Null | Meaning |
|---|---|---|---|
| `procedure_document_id` | `uuid` | **yes** | The workspace document that is this ritual's written procedure. `NULL` means no procedure, which is the state every existing row starts in and the state FR-017 requires to render exactly as before. |

Everything else on the table is unchanged: `name`, `description` (retained and still shown —
FR-005), `recurrence_rule`, `completion_window_hours`, `timezone`, `is_archived`,
`created_by_employee_id`, `last_generated_date`, `generation_window_days`, `updated_at`,
`schedule_version`.

### Constraint

```sql
ALTER TABLE collaboration.ritual_definition
    ADD CONSTRAINT fk_ritual_definition_procedure
        FOREIGN KEY (organization_id, procedure_document_id)
        REFERENCES docs.document(organization_id, id)
        ON DELETE RESTRICT;
```

- **Composite and organization-leading**, per Constitution I. A single-column
  `REFERENCES docs.document(id)` is forbidden on a tenant table and would also permit a
  cross-organization attachment that FR-003 forbids — the composite key makes that
  unrepresentable rather than merely validated.
- **`ON DELETE RESTRICT`**, matching the existing `fk_task_description` on
  `collaboration.task.description_document_id`. Documents are soft-deleted
  (`SoftDeleteDocument` sets `is_deleted = TRUE`), so this never fires in normal operation;
  it exists so a future hard delete cannot leave a dangling reference. `ON DELETE SET NULL`
  was rejected because it would silently turn "the procedure was deleted" (FR-022's visible
  loss) into "there was never a procedure" (FR-017's silent absence) — the two states the
  spec is most insistent must not be confused.

### No index

The column is only ever read *from* a definition already located by primary key. Nothing asks
"which definitions use this document", so an index on it would be an index nothing reads.
FR-004 (one document, many definitions) needs no uniqueness and therefore no unique index —
which is also why this change adds no unique key that would have to lead with
`organization_id`.

### Migration

`backend/database/migrations/20260904000002_ritual_procedure_document.up.sql`, forward-only,
idempotent (`ADD COLUMN IF NOT EXISTS`, and the constraint guarded so a replay of a dirty
version succeeds). `backend/database/scripts/schema.sql` is regenerated by
`backend/scripts/regen-schema.sh` and never hand-edited.

## Unchanged entities, and why

| Entity | Change | Why not |
|---|---|---|
| `docs.document` | **none** | FR-002: the attachment is a reference. The document does not know it is being used as a procedure — no `is_procedure` flag, no back-reference, no type. That is what lets FR-004 hold (one document, many definitions) with no bookkeeping. |
| `docs.document_access` | **none** | FR-018's implicit read is a *path*, not a row. Writing grants here would violate FR-021 by putting the document in the reader's tree, and would need maintaining every time an assignee changes. See [research.md D1](./research.md#d1-where-the-read-is-served-from). |
| `collaboration.task` (ritual instance) | **none** | FR-016: an instance resolves the procedure through its definition, so a corrected procedure reaches every open instance with no write. A `detached_from_ritual` instance has no `ritual_definition_id` to resolve through and therefore reports no procedure, satisfying that edge case with no code. |
| `collaboration.evidence_requirement` | **none** | Per-requirement procedures are out of scope. |
| `collaboration.evidence_submission` | **none** | FR-016 explicitly forbids recording which revision was live. |
| notification types | **none** | No notification is added (spec Assumptions, FR-010). |

## Derived state: `RitualProcedure`

Not stored anywhere. Resolved on read, from the column plus one point read of
`docs.document`:

| Field | Source | Notes |
|---|---|---|
| `document_id` | the column | Present whenever the column is non-null, **including when the document is unavailable** — that is what lets FR-022's unavailable state be told apart from FR-017's absence. |
| `title` | `docs.document.title` | The **current** title (FR-012). Empty when unavailable. |
| `status` | `docs.document.status` | `ACTIVE`, `OUTDATED` or `ARCHIVED`. Surfaced to the reader (FR-024). |
| `is_available` | `GetDocumentByID` succeeded | False when the document is soft-deleted or otherwise unresolvable. |

Resolution rules:

- Column `NULL` → the whole `RitualProcedure` is absent. Clients render nothing (FR-017).
- Column set, read succeeds → all four fields populated.
- Column set, read fails → `{document_id, is_available: false}`, empty title and unspecified
  status. Clients render the unavailable state; nothing about evidence submission, decisions
  or instance completion is blocked (FR-023).

The resolution never throws. A docs failure degrades one entry point; it does not fail
`GetRitualDefinition`, because that would take the whole ritual instance screen down with it.

## Validation rules (write path)

Applied in `internal/collaboration` before the column is written. Read through
`DocsLogic.GetDocument`, so a document in another organization is indistinguishable from one
that does not exist.

| Rule | Source | Failure |
|---|---|---|
| Caller is `owner` or `admin` on the definition's project | FR-006, US2 AC5 | bare `PermissionDenied` |
| Document resolves in the caller's organization | FR-002, FR-003 | `InvalidArgument` + `BadRequest` field violation on `procedure_document_id` |
| `document_type = 'workspace_doc'` | FR-003, edge case | `InvalidArgument` + `BadRequest` field violation on `procedure_document_id` |
| Document not soft-deleted | FR-002 | as above (it does not resolve) |
| Any `status` accepted, `archived` included | FR-024 | — |
| Empty string → detach | FR-009, D11 | never fails; the document is not touched |

No validation runs on the read path beyond the project-access check: a document that has
since been deleted or archived is reported, not rejected.

## State transitions

The attachment has three states and every transition is a single `UPDATE` of one column.

```
        attach (doc A)              attach (doc B)
  none ───────────────► A ──────────────────────────► B
    ▲                   │                              │
    └───────────────────┴──────────────────────────────┘
                    detach (empty string)
```

- **Replace is one write, not delete-then-add** — FR-001's "never two procedures" is a
  property of the column being singular, not of ordering.
- **Archiving the definition** does not touch the column; unarchiving restores nothing
  because nothing was removed.
- **Deleting the definition** takes the column with it, which is what ends the implicit
  access (FR-020).
- **Deleting the document** changes no state here. The column keeps pointing at a row that
  reads as unavailable — see the derived state above.
