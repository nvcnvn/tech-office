# Implementation Plan: Prune Reserved-But-Unused Values

**Branch**: `062-prune-reserved-values` | **Date**: 2026-09-12 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/062-prune-reserved-values/spec.md`

## Summary

Delete seven sets of inert values that the running system permits but never produces: two
channel kinds (`crm_deal_notes`, `support_ticket`), two file-attachment contexts
(`support_ticket`, `crm_deal`), one sign-in credential kind (`biometric`), four
notification source domains (`crm`, `hr`, `support`, `finance`), thirteen empty Postgres
schemas, three permanently disabled web navigation entries (CRM, Finance, HR), and the
entire legacy-route branch of shared-link resolution together with its `LegacyNormalized`
flag.

The technical approach is a single coordinated change set across all four layers that
declare each set — database CHECK constraint, Go constant, proto enum, TypeScript union —
as Constitution principle VIII requires, plus one forward-only migration that first proves
no stored row holds a removed value and then tightens each constraint in the same
transaction. No compatibility path, no deprecation window, no `reserved` proto markers:
the project's standing position is that a breaking change ships atomically across backend,
web and mobile.

## Technical Context

**Language/Version**: Go 1.24 (backend), TypeScript 5.x (web + mobile + shared packages),
SQL (PostgreSQL 16)

**Primary Dependencies**: Connect-RPC + protobuf (`backend/rpc/v1`), sqlc (generates
`backend/database/models.go` and `*.query.sql.go`), Next.js 15 + MUI v7 (web), Expo Router
55 (mobile), `pgx` (database driver)

**Storage**: PostgreSQL, forward-only migrations in `backend/database/migrations/`;
`backend/database/scripts/schema.sql` is a generated snapshot regenerated by
`backend/scripts/regen-schema.sh` and is never hand-edited

**Testing**: `make test-backend` (Go integration tests in `backend/integration` against a
live Postgres, `testWorld` pattern), `make test-frontend` (Playwright E2E in
`frontend/apps/web/e2e`), `make test-mobile` (Maestro flows), `pnpm run typecheck:mobile`
(the one CI-enforced quality gate, `.github/workflows/checks.yml`)

**Target Platform**: Linux server (Docker Swarm), modern browsers, iOS 15+ / Android
API 26+

**Project Type**: Multi-tenant web service with web and mobile clients in one monorepo

**Performance Goals**: No change. This is a pure removal; nothing on a hot path is
touched. Dropping thirteen empty schemas removes catalogue entries only.

**Constraints**: The change must be atomic across `backend/`, `frontend/apps/web` and
`frontend/apps/mobile` — a layer that permits a value another layer rejects is the exact
defect this feature exists to remove. Each constraint must be tightened only after the
same migration has established that no row violates it.

**Scale/Scope**: ~20 source files, 1 migration, 1 schema regeneration, 1 sqlc
regeneration, 1 proto regeneration, 5 domain documents.

### Resolved unknowns

All [NEEDS CLARIFICATION] items were resolved during Phase 0 research against the code;
the reasoning is in [research.md](research.md). The decisions taken are:

- **Proto enum values are deleted outright, not marked `reserved`.** [ASSUMPTION: `reserved`
  exists to stop a future author reusing a tag number that an old client still understands.
  There are no old clients — all three surfaces ship together — so a `reserved` marker
  would be exactly the kind of inert value this feature removes. Surviving tag numbers keep
  their current values; renumbering them would be churn with no benefit.]
- **Migration is one file, `20260912000003_prune_reserved_values.up.sql`,** following the
  repository's forward-only, `.up.sql`-only convention (no `.down.sql` files exist).
- **Emptiness is proved inside the migration**, with a `DO $$ ... RAISE EXCEPTION` guard
  per constraint, so a non-empty table aborts the migration rather than leaving a violated
  CHECK. [ASSUMPTION: this is preferable to a separate audit script, because a script can
  be skipped and a guard in the transaction cannot.]
- **`muted_domains` is repaired in the same migration** with an array-subtraction update
  before its CHECK is tightened, satisfying FR-010.
- **The thirteen empty schemas are dropped with `DROP SCHEMA ... RESTRICT`**, not
  `CASCADE`. RESTRICT fails if anything is in them, which is the emptiness proof FR-009
  asks for, expressed in one statement.

## Phase 1 — Design & Contracts

Complete. See [data-model.md](data-model.md), [contracts/](contracts/) and
[quickstart.md](quickstart.md).

Design decisions worth stating here:

1. **One migration, guarded, in dependency order.** Audit first (`RAISE EXCEPTION` if any
   row holds a removed value), repair `muted_domains` second, tighten CHECKs third, drop
   schemas last. Postgres runs DDL transactionally, so a failed guard rolls the whole thing
   back and leaves the database exactly as it was.
2. **`LegacyNormalized` is removed, not defaulted to false.** Keeping a boolean that can
   only ever be false is the defect this feature removes; the spec's assumption says so
   explicitly and FR-006 requires it.
3. **Legacy link rejection reuses the existing error.** `Normalize` already returns
   `unsupported canonical or legacy path` when neither grammar matches; with the legacy
   branch gone the message becomes `unsupported canonical path`, and the RPC-level error
   surfaced to a client is unchanged. FR-011 and Constitution X are satisfied without
   touching the error contract.
4. **Web navigation shortcuts renumber implicitly.** The `enabled: false` entries carried
   `⌘9`, `⌘-` and `⌘=`; deleting them leaves `⌘1`–`⌘8` contiguous with no gap, which is
   what SC-003 asks for. No renumbering of the surviving entries is needed.
5. **The `enabled` flag itself stays.** Every surviving entry has `enabled: true`, so the
   field is now constant — but removing it would also remove the `permission`-gated
   rendering path it shares, which is live behaviour. [ASSUMPTION: the flag is left in
   place because collapsing it is a refactor of live navigation logic, not a prune of an
   inert value, and FR-011 forbids changing live behaviour. Recorded so a reviewer can
   disagree cheaply.]
6. **`upload_context` is untouched.** Its unreachable `calendar` value has a different
   cause and is explicitly out of scope per the spec.
